# SQLite benchmark and stress-test plan

 1. Scope and setup

 Run SQLite on a filesystem mounted over the ublk device. Reuse SQLite’s existing benchmark tools;
 the lab manages setup, execution, verification, and cleanup.

 Use disposable backing files and a fresh filesystem per case. Bound runtime and cumulative
 physical writes, leaving room for checkpointing and cleanup. Do not change global cache settings
 or run performance measurements alongside other workloads.

 Pin the SQLite version and benchmark sources. Use SQLite 3.51.3 or newer, which includes the
 WAL-reset fix.

 Test three configurations:
 - DELETE journal with synchronous=EXTRA: durable rollback-journal baseline.
 - WAL with synchronous=FULL: durable per-transaction commits.
 - WAL with synchronous=NORMAL: application profile with weaker power-loss durability.

 Start with 4 KiB SQLite pages, a fixed cache budget, and mmap disabled. Record effective settings.

 2. Benchmarks and stress workloads

 Use speedtest1 for mixed SQL workloads: inserts, indexed queries, updates, and deletes. Report
 individual test results rather than only a combined score.

 Use kvtest for sequential and seeded random BLOB reads and updates. Compare small and multi-page
 values, and single-transaction runs against per-operation commits.

 For WAL tests, run enough bounded updates to cross the automatic checkpoint threshold repeatedly.
 Include checkpoint completion in total elapsed time.

 Use fixed operation counts for performance comparisons, with deadlines as safety limits. Give
 each case a stable name and fix its seed, dataset size, value sizes, transaction size, and
 concurrency. Repeat each case three times from fresh state. Extend selected cases into longer
 stress runs only after the short runs pass. Audit SQLite’s existing multiprocess tests before
 adding custom concurrency workloads; ensure synchronization is enabled.

 3. Correctness checks

 After each workload:
 - Require successful completion and check all reported SQLite errors.
 - Run integrity_check and foreign_key_check where applicable.
 - Use available benchmark result verification; for deterministic cases, compare logical contents
   against a reference run outside the tested device.
 - Close SQLite, unmount, restart the block daemon, remount, and repeat verification.

 This first suite uses clean shutdown and restart only. Crash injection, power-loss claims, and
 acknowledged-commit durability testing are out of scope.

 4. Measurements and acceptance

 Use the same result format and phase names as tests-with-rocksdb.txt. These plans compare each
 database against its own previous runs, not SQLite transactions against RocksDB operations.

 Time initialization, workload, final drain and close, validation, clean device restart and remount,
 and reopen plus revalidation separately with a monotonic clock. Also record full case elapsed
 time, including filesystem setup and cleanup. For WAL, final drain includes a completed checkpoint;
 record its result. Report workload time and workload-plus-drain time separately. Keep validation
 outside benchmark timings and label stress timings that include built-in verification.

 Record completed operations, operations per second, and latency percentiles where the tool
 provides them. Collect per-phase deltas for actual ublk reads, writes, flushes, and backing bytes
 written. Record unavailable metrics as unavailable, not zero. Label cache conditions; do not claim
 device-read performance unless reads reach ublk.

 Save one machine-readable JSONL result per case repetition under a unique evidence run directory,
 alongside raw tool output and commands. Record case name, seed, operation count, dataset and value
 sizes, transaction size, concurrency, effective SQLite settings, tool versions and build options,
 block-device commit and dirty state, kernel, filesystem and mount options, backing geometry and
 medium, cache conditions, phase timings, device counters, and validation results. Preserve failed
 and timed-out runs with their status and partial measurements; never count them as completed runs.

 Correctness passes only if verification succeeds before and after restart, with no unexplained
 errors, corruption, hangs, or leaked resources. Only correctness-passing runs qualify for the
 performance baseline.

 Keep an explicitly selected baseline run; do not overwrite it automatically. Report all three
 samples, their median and range, and percentage changes in workload time, workload-plus-drain time,
 throughput, and available tail latency against that baseline. Compare only matching workloads,
 settings, hardware, and cache conditions. Record intentional differences, including the tested
 block-device commit. Database or benchmark upgrades require a new baseline.

 Three repetitions are an initial noise check, not proof of a small improvement. Rerun apparent
 changes when they overlap observed variation; use interleaved baseline and candidate runs when
 practical. Set regression thresholds only after measuring repeatability. Do not claim sustainable
 throughput from a short run or improvement from timing alone when correctness fails.
