# v1.3 initial benchmark comparison

Date: 2026-09-20
Status: comparison planned after ADR-06 acceptance; host-ext4 duration calibration authorized separately

v1.3 follows v1.2.3. ADR-06's old version labels identify historical delivery
stages. Performance runs consolidate the existing per-case work allocation:
three runs of 32,768 requests total 98,304, rounded up at the user's request
to one run of 131,072 requests (128 Ki). Keep the initial
dataset at 8,192 records and initialize it once. Setup savings do not increase
the measured request budget. This does not change ADR-06's correctness
repetition gates. Repeat a performance run only to investigate a failure or
an apparent difference; one run does not establish repeatability.

## Existing workloads plus scan/insert cases

| Case | Database | Logical request mix | Durability |
|---|---|---|---|
| sqlite-a | SQLite | 50% reads, 50% updates | WAL, synchronous=FULL |
| rocksdb-a | RocksDB | 50% reads, 50% updates | WAL enabled, sync=true |
| sqlite-f | SQLite | 50% reads, 50% read-modify-write requests | WAL, synchronous=FULL |
| rocksdb-f | RocksDB | 50% reads, 50% read-modify-write requests | WAL enabled, sync=true |
| sqlite-e75 | SQLite | 75% scans, 25% inserts | WAL, synchronous=FULL |
| rocksdb-e75 | RocksDB | 75% scans, 25% inserts | WAL enabled, sync=true |

Retain A and F and add E75 as the only scan/insert profile. Each case loads 8,192
records (32 MiB of value payload), then executes 131,072 logical requests with
one worker, seed 123 and no rate limit. Each record has one constant-length
4,096-byte value, excluding
the key and database encoding. Set both `fieldcount=1` and `fieldlength=4096`;
upstream defaults are ten 100-byte fields. The workload properties live under
[`tools/go-ycsb/workloads`](../tools/go-ycsb/workloads/).

For A and F, retain hashed key order. F performs a read followed by an update,
not an atomic transaction. Count logical requests separately from database
calls, and verify that updates change values.

For E75, insert increasing keys with 20-digit zero padding and `insertorder=ordered`.
Request 16 consecutive records per scan, with both scan-length bounds set to
16. Choose scan starts uniformly from the initial loaded key range, matching
the pinned generator's behavior. New inserts extend the ordered key space;
they do not expand that generator's scan-start range. Count actual returned
records and bytes, including short scans at the end. The supplied upstream E
file uses `maxscanlength=1`, so it is unsuitable unchanged.

Mix percentages are selection probabilities. At the expected 25% insert share,
E75 adds 128 MiB and returns approximately 6 GiB of scan payload. These
are application bytes, not claims about disk I/O. Ordered inserts are logically
append-only; database journals, indexes and compaction still rewrite blocks.

Keep a 4 GiB filesystem as the initial candidate size. Calibrate filesystem
headroom, transient database space, cumulative backing writes and child
deadlines before the full run. If it cannot fit, increase geometry for
all paired runs and record the change; do not silently shorten one candidate.
The earlier 8 GiB backing suggestion is not a validated budget for these longer
runs. The current finite append log cannot support aged steady-state testing.

## Memory and 4 KiB geometry

The [VM environment decision](WORKBENCH-VM.md) records why we use QEMU/KVM,
the shared memory boundary, separate OS/test disks and CPU isolation requirements.

Run the entire stack inside a fresh KVM guest: kernel, filesystem cache,
go-ycsb, database and either our block daemon or LVM-VDO. Start sizing at
320 MiB, with one vCPU, no balloon device and no swap (including zram).
Increase RAM in 64 MiB steps until every selected stack completes load,
workload, drain and validation without OOM or allocation failures. Include
PostgreSQL in sizing; do not assume it is the largest consumer before measuring.

Choose one common RAM size from that calibration and use it for every paired
comparison, including both 128 MiB and 4 GiB logical devices. Device capacity
does not set guest RAM. Backing-store capacity remains a separate, larger
write-budget decision. Record configured RAM and guest `MemTotal`, which is
smaller because of kernel reservations. The host cgroup calibration is
historical; it is not the selected benchmark machine.

Use QEMU with KVM directly. A separate guest kernel gives the whole-machine
RAM boundary required here; the lab does not need an OCI container runtime.
Kata Containers also uses VMs, but adds a container-runtime interface and guest
agent. Keep all paired results on the same virtual hardware and identify them
as VM measurements, not bare-metal throughput. Host QEMU overhead is outside
the configured guest RAM and must be reported separately.

Use these initial database settings, subject to a recorded guest preflight:

| Layer | Setting |
|---|---|
| SQLite | One connection; page_size=4096 before creation; cache_size=-16384 (16 MiB suggested page-cache limit); mmap_size=0; WAL/FULL; wal_autocheckpoint=1000 |
| RocksDB | One column family; explicit 16 MiB block cache with index/filter blocks charged to it; write_buffer_size=16 MiB; max_write_buffer_number=2; mmap off; automatic compaction on; WAL/sync on; compression off |
| Guest | QEMU/KVM starts at `-m 320M -smp 1`; calibrate one common RAM size; swap disabled; no balloon; fresh guest per case |
| Workload process and file cache | Share the fixed guest RAM; record anonymous and file-cache usage; no host-global cache drops |
| Block implementation | Run our daemon or VDO inside the guest RAM budget; also record their individual memory use |
| Virtual storage | Require direct host I/O (`cache=none`); preserve guest flushes; expose 4096-byte logical and physical sectors |

The original 32 MiB dataset can still fit in this machine. It is not an accepted
I/O-stressing configuration. Calibrate database overhead and actual block reads
before choosing a larger initial dataset. Keep 131,072 measured requests; loading
more records is a separate workload change, not a consequence of consolidating
repetitions. The final dataset size remains open.

The database caches are not total process-memory limits. Read back effective
settings and record cache hits/misses, cgroup anonymous/file memory, reclaim,
memory pressure and OOM events. An OOM invalidates the run. Measure backing
reads and CPU time before claiming that I/O limits throughput. Load and run
must occur inside the same guest. Do not put the database on a host-shared
filesystem. See [SQLite's cache controls](https://www.sqlite.org/pragma.html#pragma_cache_size),
[RocksDB memory accounting](https://github.com/facebook/rocksdb/wiki/Memory-usage-in-RocksDB)
and the [kernel cgroup documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory).

A disposable host-ext4 experiment verified the page-cache mechanism independently:
two reads of a 192 MiB file caused zero process-accounted storage read bytes
under a 256 MiB cgroup, and 192 MiB per pass under a 64 MiB cgroup. Both runs
disabled swap, completed without OOM and removed their fixtures. This is a
kernel-cache probe, not a database benchmark or a guest acceptance result.
See the [256 MiB result](../evidence/page-cache-256m-probe-2026-09-20.json) and
[64 MiB result](../evidence/page-cache-64m-probe-2026-09-20.json).

The [KVM boot probe](../evidence/vm-256m-1789931259345264680/console.log) passed
with ublk, ext4 and XFS available. The pinned generic kernel reported
206,300 KiB `MemTotal` and 147,896 KiB `MemAvailable` before any database started.
Swap was absent and the guest powered off cleanly. This verifies boot
prerequisites, not database operation within the budget.

VDO is part of guest sizing: the [kernel requirements](https://docs.kernel.org/admin-guide/device-mapper/vdo.html#memory-requirements)
list 38 MB of fixed memory plus approximately 150 MB for the minimum block-map
cache, before the deduplication index. Increase the common guest RAM if needed;
do not put either storage backend outside the guest. Sizing probes do not
qualify as paired benchmark runs until every stack uses the selected RAM size.

The accepted ublk runs already advertise and check 4096-byte logical and physical
sectors. Their ext4 output reports 4 KiB blocks; XFS reports `bsize=4096` and
`sectsz=4096` for data and log. Current formatters discover device geometry;
they do not receive explicit size flags. See the [ext4 evidence](../evidence/sqlite-1789919055507253962/speedtest-main--wal-full--repetition-1/commands.log)
and [XFS evidence](../evidence/sqlite-1789919057604434536/speedtest-main--wal-full--repetition-1/commands.log).

The comparison runner must require 4 KiB logical sectors on both paths before
formatting, record physical sector and minimum-I/O sizes, and set filesystem
blocks explicitly: `mkfs.ext4 -b 4096` and `mkfs.xfs -b size=4096 -s size=4096`.
Verify the resulting filesystem geometry. An ext4 block-size option does not
change the block device's logical sector size. Configure VDO's minimum I/O
size as 4096, with 512-byte emulation disabled.

## LVM-VDO comparison and physical space

Keep four storage scenarios. Each runs A, F and E75 on SQLite and RocksDB:

| Scenario | Benchmark cases |
|---|---:|
| ext4 baseline on LVM-VDO | 6 |
| XFS baseline on LVM-VDO | 6 |
| Our block device with ext4 | 6 |
| Our block device with XFS | 6 |

The total is 24 performance runs, one run per case. The baseline rows use
LVM-VDO as previously requested. The host-ext4 duration probe is calibration,
not an additional permanent scenario. VDO provides thin provisioning itself; an
additional dm-thin layer is not required for this first comparison. Keep
compression and deduplication disabled initially. Enable compression on both
paths only after our compression implementation is ready, using separately
identified value-compressibility profiles. Database-level compression stays
disabled. Record value-generation identity and duplicate content.

The requested historical comparison adds v1.0 and v1.1 on our device, each
with ext4 and XFS. Reuse the two baseline scenarios rather than repeating
them for every version: three device versions times two filesystems plus
two baselines means eight scenarios, or 48 runs. Pin exact commits and build
each release separately. Always format fresh images with that release;
persistent formats are incompatible. The latest candidate is the completed
v1.3 implementation, not an unverified release tag. Historical compatibility
and the total duration remain unmeasured.

Use the same physical storage medium, filesystem capacity, filesystem features,
mount options, database builds and workload memory limits. Record the complete
device stack. Set and record the same discard policy: no mkfs discard, online
discard or timed trim in this initial comparison. Later trim measurements are
separate because our device currently has no discard/reclamation support.

Measure space before formatting, after filesystem creation, after load, during
the workload at five-second intervals, and after drain/close. Keep these distinct:

| Quantity | Evidence |
|---|---|
| Application and filesystem use | Record count/value bytes, database file sizes and allocated file blocks, filesystem used/free bytes |
| Our device's consumed storage | Allocated log extent including obsolete records and metadata; current live payload separately; reserved backing capacity separately |
| VDO consumed storage | Raw `vdostats --all` data/overhead/used-block counters with reported block size; absolute use and growth from the empty-volume baseline |
| Underlying allocation | LVM physical extents reserved; dm-thin allocated chunks if present; allocated host-file blocks for file fixtures |

Cumulative bytes written are write amplification, not occupied space. A linear
LV reserves its full capacity even if our log has consumed only a prefix. Do
not present that prefix as reclaimed host storage. Report fixed metadata,
peak use, final use and consumed-storage/live-payload ratios for both paths.
Do not infer device occupancy from `df` or a block node's `st_blocks`.

VDO has substantial fixed metadata costs; the kernel documentation describes a
3 GB minimum reservation. Size its backing separately after checking the local
version and configuration. The supplied 128 MiB LV is not a VDO candidate.
No LVs are created, converted or formatted by this plan. Sources:
[dm-vdo geometry and metadata](https://docs.kernel.org/admin-guide/device-mapper/vdo.html),
[LVM-VDO usage counters](https://man7.org/linux/man-pages/man7/lvmvdo.7.html).

## Measurements and readiness

After changing E95 to E75, the two new host-ext4 cases measured 2.32 s load plus
19.70 s workload for SQLite, and 3.77 s load plus 22.71 s workload for RocksDB.
Reusing the unchanged A/F cases gives approximately 2 minutes 45 seconds for
one six-case portfolio, or 11 minutes for four scenarios at identical speeds.
Budget 15–20 minutes provisionally for the 24-case performance matrix; this is
a planning allowance, not an upper bound. Our-device and VDO timings, stricter
I/O-cache controls and the full correctness gates remain unmeasured. PostgreSQL
is excluded. The [updated evidence](../evidence/raw-ext4-portfolio-e75-timing-2026-09-20.json)
records both build identities and all source runs. The E75 build adds a timeout
to SQLite's setup checks; both batches use the same workload and durability
settings. E75 passed row-count checks on both databases and SQLite integrity
and value-length checks, with matching operation counts and successful cleanup.

The original 2026-09-20 host-ext4 duration calibration measured A/F/E95 at
148.86 seconds for load plus run. E95 has since been replaced by E75; retain
these measurements under their original labels:

| Database | Workload | Load | Run | Total |
|---|---|---:|---:|---:|
| SQLite | A | 2.42 s | 18.90 s | 21.32 s |
| SQLite | F | 2.37 s | 19.85 s | 22.22 s |
| SQLite | E95 | 2.37 s | 14.64 s | 17.01 s |
| RocksDB | A | 3.87 s | 32.13 s | 36.00 s |
| RocksDB | F | 3.82 s | 32.68 s | 36.50 s |
| RocksDB | E95 | 3.87 s | 11.94 s | 15.81 s |

These are process times, including database open/close. Validation and sync
probes are outside the table. Load prepares the initial data and is excluded
from workload throughput and latency. It is measured separately and included
only when estimating the full portfolio's elapsed time. Every workload phase
ran longer than its load phase. Settings were 8,192 initial records, 4 KiB values,
131,072 requests, one worker, seed 123, synchronous writes and a 256 MiB cgroup
without swap. Both databases reported matching operation counts for each
workload, and all six passed their record-count checks. SQLite also passed
integrity and value-length checks. Both temporary directories were removed.

The existing root ext4 filesystem has 4 KiB blocks over a 512-byte-sector LV;
it is not the future 4 KiB-sector comparison fixture. SQLite reads were cached
(zero filesystem input blocks during each measured run). No ublk or VDO ran.
At identical speeds, four scenarios would take 595.44 seconds (about ten
minutes), before setup and full validation. This is arithmetic extrapolation,
not measured ublk/VDO performance. The [timing evidence](../evidence/raw-ext4-portfolio-timing-2026-09-20.json)
links raw commands, counts, resource usage and the excluded first RocksDB
attempt, whose post-run verifier used an unsupported command-line flag.

Save phase-separated load, workload, drain/close, validation, restart and
revalidation times. Report logical requests/s and scan records/bytes/s. Keep
per-operation HDR histograms with count, p50/p95/p99/p99.9/p99.99 and maximum,
plus ten-second interval histograms. The pinned go-ycsb already computes
p99.99. Label these as single-client, closed-loop service latencies; they do
not represent queueing delay under a fixed offered arrival rate.

Always report sample counts. At p99.99, one million samples leaves roughly
100 observations in the upper tail. With the actual consolidated budget,
E75 has approximately 32,768 inserts, insufficient to resolve p99.99 reliably.
Retain that percentile but mark its limited sample support; do not increase
the run budget merely to support a percentile.
Do not average interval percentiles; merge histogram counts for a run total.

Keep `result.json`, raw histograms, `io.json`, `space.jsonl`, `manifest.json`,
commands and raw logs. Include physical read/write bytes, operations and flushes
at named layers, CPU/RSS, database background work, effective settings, exact
build/source hashes, kernel, geometry, cache state, content checks and cleanup.
`summary.csv` reports completed runs and matching-path ratios, without invented
between-run medians or ranges. Preserve failures and partial measurements.

The local tool patch now adds a fixed seed, synchronous writes, database cache
controls, SQLite scan ordering and correct RocksDB short-scan lengths. The host
timing runner uses a cgroup and checks synchronization calls and record counts.
Before the storage comparison, finish space accounting, I/O calibration and
independent full-content verification. The workload still discards scan
contents, so successful exit is not scan validation.
Record matching request/value-sequence hashes across paired runs. The property
files alone do not provide these controls or qualify as benchmark acceptance.

SQLite's native suite, RocksDB's native tools and PostgreSQL's lifecycle remain
ADR-06 acceptance gates. The rest of the [workbench proposal](../TMD-WORKBENCH.md)
remains later work.

The pinned go-ycsb already imports `db/pg` and registers `pg` and `postgresql`.
It can send A/F/E75 requests to a local PostgreSQL server with its data and WAL
on ext4 or XFS mounted over our device. This route is not yet accepted on our
device. Before adding it, integrate the server lifecycle and memory controls,
verify durability settings, and fix the driver's missing `ORDER BY YCSB_KEY`
in scans. Its `ON CONFLICT DO NOTHING` inserts also require independent count
checks. Record PostgreSQL's value-storage/compression settings for 4 KiB fields.

PostgreSQL is not silently included in the current duration estimate. Adding
the same three workloads on all four storage scenarios would add 12 cases,
bringing the performance matrix to 36. Native ADR-06 correctness gates,
including PostgreSQL's pgbench/checksum/restart checks, remain separate from
this performance matrix and its measured load/run time.
