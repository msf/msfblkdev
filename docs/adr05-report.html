When the backing store fails

A clean checkpoint freed six segments. Failing its descriptor write or final sync freed none. In both fault runs, the client saw the error and recovery returned the bytes it had flushed.

Arm64 qualification: passedADR-05: open
Engine: format 4 · 77fc16eGuest: Debian 13 arm64 · Linux 6.12.117+deb13-arm64Host: macOS · Lima/VZ

Which faults did we actually test?

The live ublk workload injected errors at two I/O sites: checkpoint B’s descriptor write and its final sync. It did not inject transient client reads, delayed completions or hangs. Below, each row names the call, fault, expectation and observation. Counts are scenarios, not unique test functions. Earlier campaign runs and the final arm64 rerun are identified by their linked logs.

Was it the engine or the test?

Two confirmed engine bugs: F01 let the next flush succeed after a failed backing sync. F02 refused to reopen a valid volume. Both had failing reproducers and passed after engine fixes. Before/after evidence.

No confirmed harness malfunction in these 40 rows. In the two missed-rule controls, we deliberately aimed the injector at the wrong sector. The inner run was rejected; the harness test passed. Neither run tests the engine’s response to EIO.

Invalid run ≠ failed engine. If a required injection accidentally misses, the runner crashes, or evidence is missing, record inconclusive — no engine verdict. Attribute it to a harness bug only after reproducing a fault in the test tool.

Reading the results: Red means the test found a defect. Amber means a fault, rejection or fallback was expected and the test passed. Green marks a successful outcome or verified repair. Gray means not run.

01 / Live experiment

Where does the error enter?

The client writes known values through a real ublk device and flushes them. More writes force checkpoint B, the publication that can release segments. The test pauses the writer just before the descriptor write and arms a one-shot rule beneath the engine.

  1. Callerublk client
  2. EngineRust · io_uring
  3. Via FUSEQEMU · blkdebug
  4. StorageScratch image
Compare the three recorded runs

Clean control: B published. The client write succeeded, the engine freed six segments and issued four discards. All eight logical blocks matched on reopen.

Descriptor write: QEMU rejected the 4 KiB write. The client write returned EIO. The engine freed zero segments and issued zero discards; all six candidate segments retained the same bytes and extents.

Final fsync: The descriptor write succeeded, but its sync returned EIO. The client write failed. The engine freed zero segments and issued zero discards; all eight logical blocks matched after recovery.

Pass requires the intended call to fail. A rule aimed at the wrong sector must fail the test. Recovery runs on a copy so it cannot change the evidence. Final live trace · Missed-rule control

02 / Test coverage

What counts as a pass?

Fault injection controls the error a caller sees. Deterministic simulation testing (DST) controls which bytes recovery finds. The campaign uses both because a failed sync does not say which pending writes survived.

01 · Injector calibration

Did the caller actually get EIO?

Use a fresh 4 KiB image per case. First write, sync and read back with faults off. Then fail one write or one sync. Require exactly the expected errno, a successful retry and matching bytes in the underlying file.

Probe and close-time engine results →
02 · Engine fault seam

What if I/O fails before or after completion?

Match a specific I/O opcode and occurrence during format, open or a volume operation. Check hit counts, the original errno, unchanged data where promised, and whether the next request is allowed. A zero-byte completion also exercises short-I/O accounting.

Seam and capacity controls →
03 · Deterministic crash images

Which flushed bytes must survive?

Keep or drop the pending checkpoint descriptor: recovery must pick B or A respectively and return all eight expected blocks. Separately, split one real 8 KiB append into payload and footer. Neither or payload alone yields the old value; both yield the new value. A footer alone must produce a checksum error without modifying the read buffer.

04 · Independent checks

Would the checker notice bad recovery?

A logical oracle compares caller-visible blocks with allowed histories. It rejects planted faults such as a lost flushed write or a resurrected discard. A separate read-only checker walks both checkpoint roots and their replay paths; both roots passed on each retained live-fault image.

03 / Two confirmed defects

What changed in the engine?

F01 · A backing ENOSPC let the writer continue

Before: checkpoint B’s final sync returned “no space”, but the next flush succeeded. After 9f3d309: the caller still gets ENOSPC and the volume stops serving I/O. A capacity refusal before backing I/O still leaves it usable. Failing run · Same test after repair

F02 · Clean close could leave a volume unable to reopen

Two seeded workloads exposed intact older metadata at a reused address. Recovery mistook it for damage. After 77fc16e, recovery accepts that stale case only after checking its address, age, framing and checksum. All six seed/cache combinations passed, each checking 680 logical blocks per epoch. Damaged and misplaced records still failed closed. Original matrix · Repaired matrix

05 / ADR still open

What would close ADR-05?

  1. Implement the accepted retry contract. Hold later work while an I/O is uncertain. Give transient operations up to three attempts, with 50/250 ms backoffs and one shared 5 s caller deadline. Allow up to 30 s more to reconcile a stalled operation; resume only on the same exclusively owned backing object, otherwise fence. These are design defaults, not measured results. Decision and safety conditions.
  2. Fill the engine-facing matrix. Exercise positive-length short operations, storage timeout/disappearance, and remaining normal-I/O and recovery EIO/ENOSPC cases. Extend reuse, growth, decoder and cleaner scheduling coverage.
  3. Qualify other environments. Run the supported native amd64 and Linux-host configurations. With operator approval, capture and replay medium faults and check filesystem and database recovery against external histories. These tiers have not run here.
  4. Accept and ship. Resolve or explicitly defer each remaining criterion, merge the accepted work and identify the delivered revision. A passing guest run is not physical power-loss evidence.
