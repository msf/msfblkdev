ADR-05 / format 4 / test history

Fault test timeline

This software presents a disk to an application and stores its contents in a backing file. A successful write means the engine accepted the bytes. A successful flush is a stronger promise: if the backing storage honors its own successful syncs, the client must get those bytes back after a restart, unless a later write or discard changed that block. These tests ask what happens when a storage operation fails or only some bytes reach disk.

35/35 passed (100%) in the latest focused run at 4887389. Eight guest-only cases were not rerun. The full developer suite did not pass: its Linux filesystem test ran out of space (ENOSPC) during setup, outside the focused fault tests. Failure log.

FSYNC-01: read the first row from left to right. At c2ceb37 the default engine safely refused the flush but failed the resume test. With library retry enabled it passed at 067fd12 and again at 4887389. The default service still reports an error and stops serving requests rather than claiming the writes are safe.

Storage terms used in this report
Block and address (LBA)
A block is a numbered unit of client data. Its logical block address is the number the client uses to read or write it. The engine may store the bytes elsewhere in the backing file.
Record, checkpoint and replay
A record describes a change. A checkpoint saves the engine’s map of blocks and free space. On startup the engine reads a valid checkpoint and applies later valid records. In a flush retry, “replay” instead means writing the same saved record bytes to storage again.
Discard and reuse
A discard tells the engine that the client no longer needs data in a range. Before using the underlying space for something else, the engine must know that recovery will not need the old bytes.
EIO, ENOSPC and fencing
EIO means an input/output operation reported an error. ENOSPC means no space was available. To fence a volume is to stop serving requests rather than continue from uncertain state.

02 / Test coverage

What counts as a pass?

Fault injection controls the error a caller sees. Deterministic simulation testing (DST) controls which bytes recovery finds. The campaign uses both because a failed sync does not say which pending writes survived.

01 · Injector calibration

Did the caller actually get EIO?

Use a fresh 4 KiB image per case. With faults off, write a pattern, sync it and check the bytes. On fresh images, fail one write or one sync. Check the errno, then have the probe issue another write and sync. Compare the underlying file with the expected pattern. This is a probe retry, not an engine retry.

03 · Deterministic crash images

Which flushed bytes must survive?

Build two images that differ only in the newest checkpoint descriptor. Without it, recovery must use the earlier checkpoint and keep segment 0 unavailable. With it, recovery must use the newer checkpoint and mark the segment free. In both cases all eight logical blocks must match the client history. Separately, split one real 8 KiB append into payload and footer. Recovery must return the old value if neither half survives or if only the payload survives. If both survive, it must return the new value. A footer alone must produce a checksum error without modifying the read buffer.

05 / ADR still open

What would close ADR-05?

  1. Implement the accepted retry contract. Hold later work while an I/O is uncertain. Give transient operations up to three attempts, with 50 ms and 250 ms retry delays and one shared 5 s caller deadline. Allow up to 30 s more to reconcile a stalled operation; resume only if the engine still owns the same backing object exclusively and has settled the outstanding I/O. Otherwise, stop serving requests. These are design defaults, not measured results. Decision and safety conditions.
  2. Fill the engine-facing matrix. Exercise positive-length short operations, storage timeout/disappearance, and remaining normal-I/O and recovery EIO/ENOSPC cases. Extend reuse, growth, decoder and cleaner scheduling coverage.
  3. Qualify other environments. Run the supported native amd64 and Linux-host configurations. With operator approval, capture and replay medium faults and check filesystem and database recovery against external histories. These tiers have not run here.
  4. Accept and ship. Resolve or explicitly defer each remaining criterion, merge the accepted work and identify the delivered revision. A passing guest run is not physical power-loss evidence.

Flush retry and seeded recovery tests

Can the default engine finish a flush after two writes disappear?

Setup. The client writes different values to blocks 0 and 1, then flushes. A flush asks the engine to make all earlier writes durable. Next the client overwrites both blocks and receives two successful write responses. These responses alone do not promise that the new bytes will survive.

Fault or control. On the next flush, the test restores the backing file to its previously flushed contents and returns one input/output error (EIO) instead of syncing. This removes both new records; it does not just change a return code.

Expected. To meet the new availability target, the engine must restore both writes and finish this same client flush successfully. If it cannot, it must report failure rather than claim the old values are the new ones.

Expected. The client should receive one successful reply containing the full original pattern. The second read must use the same storage address.
