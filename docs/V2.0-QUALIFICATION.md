# v2.0 qualification: format-4 space reclamation

The [v2.0 release](https://github.com/msf/msfblkdev/releases/tag/v2.0) tags `031d778` on `main`. [PR #3](https://github.com/msf/msfblkdev/pull/3) was tested at `fed4151`; the release and tested commit have the same Git tree (`2d9e806703d4a7bf15dab5dc28ba886d2d6dbcb1`). Format 3 and format 4 are incompatible. There is no in-place migration.

## What passed on the release tree?

- Linux developer and process-crash suites: 341 tests in each run. The independent checker passed 16 controls. Live ublk/fio passed eight scenarios with three repetitions. ext4 and XFS passed their lifecycle tests. SQLite passed 87 clean-restart cases on each filesystem. See the [live command results](../evidence/v2.0/live-status.log).
- Tight geometry: the formatter selected 8 MiB segments for 128 MiB logical on 185 MiB raw at 100% logical fill. After every logical block was written, the independent engine replay wrote another 555 MiB and verified all 32,768 blocks after reopen. Two previously failing sizes and a larger working control used the same 8 MiB segments. See the [controlled replay results](../evidence/v2.0/engine-replay.md).
- Historical aged-fio qualification: on separate, fully populated 4 GiB logical volumes with 6 GiB raw backing and 32 MiB segments, uniform random writes completed 24 GiB and Zipf random writes completed 54 GiB. Both reached the predefined steady-state stop without `ENOSPC`, panic, or OOM. These were one-time release measurements, not fixtures for the small functional regression. See the [fio measurements](../evidence/v2.0/aged-fio.json).

## Manual aged-fio profile (high write volume)

The [saved fio argument generator](../tools/manual-qualification/aged_fio_profile.py) does not execute fio. It is not connected to `make test`, CI, or `make test-compaction-small`. Run the large workload only by explicit operator request on a disposable device with an agreed write budget. A VM backed by a physical SSD still writes to that SSD.

For future manual runs, use `--size-mib 4096 --prealloc-mib 4915` (at most 20% extra raw capacity) on separate fresh fixtures for uniform and Zipf. Fill and flush 4 GiB, then overwrite in windows of 4,915 MiB. The release formatter accepted this geometry at 100% logical fill and chose 32 MiB segments. Only formatting was checked at this tighter size; the v2.0 endurance results above used 6 GiB raw. After at least three windows, stop when throughput and external write amplification each change by no more than 5% between adjacent windows, or after ten windows. The two release runs issued **86 GiB of client writes** including both fills. Actual backing writes can be much higher; budget and monitor backing-device bytes, not just client bytes. The profile takes an inherited device descriptor from the operator's fixture supervisor; it does not select or open a device by name.

## What does this establish?

The cleaner can recover space under pressure on the tested geometries. The writer repays segments borrowed from the cleaner reserve, accounts for sparse mapping pages during relocation, and publishes metadata that still pins a victim before reporting no space. `100% logical fill` means every advertised logical block is live; it does not mean the raw backing is full.

These bounded runs do not prove indefinite progress for every geometry or durability under power loss. The SQLite correctness matrices do not qualify the separate aged SQLite A/F workloads. [ADR-05](../ADR-05-GOAL-3-BACKING-MEDIUM-FAULT-RESILIENCE.md) covers proposed backing-fault tests; [ADR-06](../ADR-06-FILESYSTEM-AND-POSTGRESQL-CORRECTNESS.md) tracks the remaining database gates.
